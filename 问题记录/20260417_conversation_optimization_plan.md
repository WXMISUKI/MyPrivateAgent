## 一、当前问题诊断

### 1.1 问题汇总

| 问题 | 描述 | 根本原因 |
|------|------|----------|
| 思考内容消失 | 刷新后思考过程变成普通文本 | 思考内容和答案混在一条消息中，无法区分 |
| 内容重复 | AI 回答出现两次 | orchestrator 输出时可能重复发送了 content |

### 1.2 当前数据流程

```
用户输入 → orchestrator → SSE (reasoning + content 混合) → chat.py 保存(混合) → 前端加载(无法区分)
```

### 1.3 成熟智能体对比

| 智能体 | 思考处理 | 历史记录 | 渲染方式 |
|--------|----------|----------|----------|
| Claude Code | 实时流式到独立区域 | 只存最终答案 | 思考区 + 答案区 |
| ChatGPT | 灰色小字可折叠 | 存完整信息 | 嵌套渲染 |
| DeepSeek | `<think>` 标签 | 标签内是思考 | 结构化解析 |

## 二、解决方案

### 2.1 方案A：分离存储（推荐）

**核心思路**：将思考过程和最终答案作为独立的数据库记录存储

```
后端：
- orchestrator 输出独立的 reasoning 和 answer 消息
- chat.py 分别存储两条 Message 记录
  - role="assistant", content_type="reasoning" (思考内容)
  - role="assistant", content_type="answer" (最终答案)

前端：
- 加载历史记录时，根据 content_type 区分渲染
- reasoning → 显示在思考区域
- answer → 显示在答案区域
```

**优点**：
- 数据结构清晰
- 支持选择性显示/隐藏思考过程
- 历史记录完整

**缺点**：
- 需要修改数据库模型
- 需要修改存储逻辑

### 2.2 方案B：单条消息 + 结构化内容

**核心思路**：在单条消息中用特殊标记分隔思考和答案

```
存储格式：
content = "<<<REASONING>>>\n思考内容\n<<<ANSWER>>>\n最终答案"

前端渲染：
- 解析 "<<<REASONING>>>" 和 "<<<ANSWER>>>" 分隔符
- 分别渲染到不同区域
```

**优点**：
- 不需要改数据库
- 实现简单

**缺点**：
- 不够优雅
- 解析容易出错

### 2.3 方案C：混合方案（快速修复）

**核心思路**：暂时不存储思考过程，只存储最终答案

```
后端：
- reasoning 消息只用于 SSE 流式输出，不存数据库
- answer 消息存储到数据库

前端：
- 实时显示思考过程（流式）
- 刷新后只显示最终答案（从数据库加载）
```

**优点**：
- 改动最小
- 快速见效

**缺点**：
- 刷新后看不到思考过程

## 三、重复内容问题修复

### 3.1 问题定位

从日志分析：
```
app.js:660 [SSE] 收到数据: content {type: 'content', content: '我是DeepSeek...'}
app.js:660 [SSE] 收到数据: content {type: 'content', content: '我是DeepSeek...'}  // 重复
```

可能原因：
1. orchestrator 中的 content 被 yield 了两次
2. 前端 updateMessageContent 被调用了两次

### 3.2 修复方案

**后端修复**：
- 检查 orchestrator 是否有多次 yield content 的情况
- 确保 content 只被 yield 一次

**前端修复**：
- 在 updateMessageContent 中添加去重逻辑
- 或者使用唯一 ID 追踪消息
